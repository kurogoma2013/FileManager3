# アーキテクチャ・データ構造

## モジュール構成

- `src/main.rs`: ロギング、設定読込、DB接続、実行ディレクトリ準備、HTTPS待ち受け
- `src/routes.rs`: WebAuthn状態の構築、Axum Router、共通HTTPミドルウェア
- `src/config.rs`: `config/settings.json` および環境変数の読み込み
- `src/app_state.rs`: DBマイグレーション、初期管理者作成、起動時のストレージ整合性確認
- `src/handlers/`: HTTPリクエスト処理・認証・案件・販売店・メモ・ファイル・ユーザーのハンドラー
- `src/core.rs`: ロール別権限判定ロジック
- `src/db.rs` / `src/storage.rs`: SQLite接続共通設定、物理ファイル保存・ハッシュ管理
- `src/specifications.rs`: 管理者専用の仕様書Markdownレンダラー
- `src/templates/`: インラインHTMLテンプレート

## データ設計

- **SQLite**: 外部キー制約、トランザクション、インデックス、FTS5全文検索を活用
- **論理削除**: 案件・販売店・ファイル・ユーザー・メモは `active = 0` または `deleted_at` で管理
- **ファイル監査情報**: ファイルのアップロード実行ユーザーIDを `files.uploaded_by`、論理削除実行ユーザーIDを `files.deleted_by` に内部保存する。既存ファイルなど実行ユーザーを特定できないレコードはNULLを許容する
- **監査情報の確認**: 管理者だけがファイル操作メニューから各版のアップロード者・論理削除者を確認できる。監査取得APIも管理者専用とする
- **物理削除**: 管理者だけが削除済みデータを確認操作付きで物理削除できる。案件・ファイル削除時はDBの共有参照を確認し、未参照の物理ファイルだけを `.quarantine/` へ隔離する
- **ファイル重複排除**: 物理ファイルはハッシュ値（SHA-256）で単一管理し、DBレコードで案件・版情報を関連付け
- **整合性検査**: `cargo run -- check-integrity` でSQLiteへの接続、スキーマ、外部キー、DB参照ファイルの存在・サイズ・SHA-256、孤立ファイルを検査する。検査対象外の隔離ファイルは `storage/.quarantine/` に保持する
- **起動時復旧**: 起動時にDBから参照されないファイルと `.upload-*` 一時ファイルを自動削除せず隔離する。新規DB作成前に既存ストレージがある場合も同じ隔離方式を使う
- **物理削除の順序**: 未参照ファイルは `.quarantine/` へ移動してからDBレコードをトランザクションで削除する。DB削除に失敗した場合は元の場所へ戻す
- **担当者データ**: `dealer_contacts` に氏名、電話番号、任意のメールアドレスを保存する。メールアドレス追加時は既存行を空文字で移行する。
- **案件・販売店データ**: `projects` と `dealers` に任意のメールアドレスを保存する。追加時は既存行を空文字で移行する。
- **ユーザー日時**: `users.created_at` は登録履歴として保持し、管理画面・APIには `users.updated_at` を更新日時として表示する。既存DBはマイグレーションで登録日時を初期値に引き継ぐ。
